# AGENTS.md — инструкции для AI-агентов, работающих с CallLens

CallLens — русскоязычный MVP-сервис разбора sales-звонков: FastAPI-бэкенд
(`backend.py`), статический фронтенд (`index.html`, `app.js`, `styles.css`,
`dashboard.*`), multi-tenant авторизация без паролей (`auth_*.py`) и системный
промпт анализа в `prompt.md`.

## Запуск

```bash
python3 -m venv .venv && source .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env                                   # заполнить OPENAI_API_KEY
export DATABASE_URL=sqlite+aiosqlite:///./calllens_auth.db
alembic upgrade head
uvicorn backend:app --reload --port 8000
```

Локальные внешние зависимости: `ffmpeg`/`ffprobe` (чанкование аудио >25 МБ и
длительность). Без `OPENAI_API_KEY` AI-режим недоступен; для проверки UI-пути
используйте `CALLLENS_DEMO_MODE=1` (детерминированный fixture, не оценка
реального звонка).

## Тесты

```bash
pytest            # конфигурация в pytest.ini, asyncio_mode=auto
```

Тесты используют SQLite (`calllens_auth_test.db`) и `EMAIL_MODE=log`; реальные
SMTP/OpenAI-вызовы в тестах запрещены. Перед коммитом `pytest` должен быть
зелёным.

## Стиль кода и структура

- Бэкенд — плоская структура модулей в корне репо: `backend.py` (анализ),
  `auth_routes.py` / `auth_models.py` / `auth_db.py` / `auth_settings.py` /
  `auth_mail.py` (авторизация). Не создавайте новые пакеты без необходимости.
- `backend.py` написан в плотном компактном стиле (короткие строки, inline
  default'ы) — соблюдайте его при правках этого файла; `auth_*.py` — обычный
  читаемый стиль с type hints.
- Все пользовательские строки — на русском. Названия четырёх стилей клиента
  фиксированы: «Результатный стратег», «Доказательный эксперт»,
  «Визионер-вдохновитель», «Надёжный партнёр» (маппинг в `STYLE_LABELS`).
- LLM-ответы нормализуются в `normalize()` — любое новое поле API должно иметь
  там дефолты, чтобы старый/неполный ответ провайдера не ломал отчёт.
- Расширения API обратно совместимы: только добавляем поля, не переименовываем
  и не удаляем существующие.

## Безопасность

- Секреты — только через env-переменные (`.env`, `.env.example`); никогда не
  хардкодить ключи и не логировать их. Наличие ключа наружу — только boolean
  (`ai_configured` в `/api/health`).
- Аудио и транскрипты клиентов не отправлять никуда, кроме выбранного
  пользователем LLM/Whisper-провайдера. Не использовать реальные записи
  клиентов в тестах и демо-данных.
- Мультитенантность: запросы к БД фильтровать по `tenant_id`; для PostgreSQL
  вызывать `set_tenant_scope()` (RLS). Не добавлять эндпоинты в обход
  `current_context` / `require_roles`.
- Чек-листы пользователя хранятся в `localStorage` браузера — не отправлять их
  в сторонние сервисы.

## Правила психотипирования (обязательны для любого анализа)

Приоритет имеют нативные модульные правила в `.qoder/rules/`:
`psychotype-disc.md`, `psychotype-big-five.md`, `sales-objections-laer.md`.
Ключевые принципы (кратко):

1. **Evidence-based**: каждый вывод о психотипе сопровождается точной цитатой
   из транскрипта и тайм-кодом. Нет цитаты — нет вывода; вместо него
   `confidence` снижается, а профиль помечается как гипотеза.
2. Оценивается **наблюдаемый коммуникационный паттерн** в конкретном звонке,
   а не личность: запрещены клинические, кадровые, демографические выводы и
   утверждения о «неизменном характере».
3. DISC (D/I/S/C) и Big Five (O/C/E/A/N, шкала 0–100) выводятся только по
   речевым паттернам клиента: темп и длина реплик, лексика (цифры/эмоции/
   статус/гарантии), структура аргументации, реакция на давление и риски.
4. Каждый вывод должен содержать контрдоводы (counter-evidence), если они
   наблюдались; при `confidence < 0.55` профиль формулируется как гипотеза.
5. Методологии MBTI, Enneagram и коммерческие скоринги (Humantic AI, Crystal,
   FDNA, Second Opinion for Sales, EQALL) в runtime не используются: у них
   закрытые лицензии/валидность спорна. Допустимо упоминать их в документации
   как контекст, но не копировать их тексты и шкалы в код и промпты.
